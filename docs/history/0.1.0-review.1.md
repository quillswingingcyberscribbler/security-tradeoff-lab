# Historical review — 0.1.0-review.1 / workbook v6.1

Review date: 22 October 2026. Source: `Opportunity-Cost-Security-Model-v6.1.xlsx`.

## Verdict

The workbook has a useful and distinctive decision model: review one current security activity against a specific proposed change, then keep employee attention, specialist capacity and cash separate. The examples make the distinction concrete. Their aggregate time-valued annual benefit is €738,250, while their recurring cash change is **minus €70,000**. The model therefore does not confuse a positive economic estimate with a budget saving.

The supplied version is suitable for a documented development prerelease. It is **not ready for a stable decision-support release**. Its core example arithmetic reproduces, but readiness messages and several eligibility gates do not match the user guidance. A spare-row review-key defect can prevent an explicit blocker reaching the decision view.

The source file is preserved unchanged. Corrections below are proposed, not applied.

## Verification

The package contains nine worksheets and 636 formula cells. Its ZIP and XML are intact, all formula cells have saved cache elements, and no saved error cells, macros or external workbook-link parts were found. Empty-string formula results are deliberate in unused rows. All sheets use passwordless protection, which helps prevent accidental edits but is not access control.

A disposable copy was recalculated through the bundled LibreOffice development build. All 636 formula results agreed with the source caches, with no error cells. A separate purpose-limited, read-only interpreter then evaluated the source formulas: **636 of 636 baseline results matched** the recalculated workbook. Eighteen input scenarios reproduced their stated observations. Ten demonstrate expected behavior and eight reproduce defects or incomplete gates. Passing a defect-reproduction assertion means the defect was reproduced; it does not mean the workbook is correct.

The scenario interpreter reads formulas with openpyxl and keeps changed inputs in memory. It never saves a workbook. This is independent formula evaluation, not native Microsoft Excel testing. Native Excel interactions, every conditional format, every dropdown, and exhaustive legal or standards coverage were not certified. An artifact-engine preview was attempted but rejected because its calculated values disagreed with both the saved source and the independent LibreOffice recalculation. It is not included as evidence of workbook values or native Excel layout.

## What works

- The baseline examples reconcile to €1,393,050 current annual cost, 11,753.33 net staff hours, 938 net team hours, minus €70,000 recurring cash change, and €738,250 time-valued benefit.
- Live portfolio totals start at zero; the eleven supplied activities are explicitly labelled Example.
- The workload responds to the shared headcount driver. Doubling the employee count doubles case 1 execution hours from 7,333.33 to 14,666.67.
- Direct annual hours mode works independently of event frequency and headcount.
- A blank alternative licence cost produces `unknown` and excludes the case; an explicit zero remains a valid known zero.
- An explicit rejected decision and a correctly linked blocked challenge review exclude a case.
- A hypothesis cannot be promoted to a validated forecast merely by changing the status.
- A zero remaining share on scope reduction means complete removal, while a blank share remains unknown.
- Realized status with missing numeric actuals is excluded from planning, although the corresponding warning is broken.

These are meaningful strengths. They preserve the distinction between an analytical suggestion and the proposal actually selected, and between a forecast and measured results.

## Release blockers

### OC-01: The entire readiness column is empty

**Evidence:** `Review & Decision!AC6:AC20` contains neither formulas nor explanatory text. Its heading promises readiness guidance. `Start!C19` and `Review & Decision!C40` count messages beginning `Realized claimed` in that empty range.

**Reproduction:** set `Cases!AK6` to `realized` and leave AL6:AN6 blank. `Review & Decision!AB6` correctly becomes `no`, but `Start!C19` still says `OK - realized entries are measurement-backed.` The warning is therefore falsely reassuring even though the eligibility gate catches the missing numbers.

**Correction:** restore a complete readiness formula in every working row. It should identify missing proposal, incomplete workload/cost inputs, missing model inputs, blocked or incomplete review, rejected decision, insufficient evidence, and missing actuals as applicable. Derive the Start warning from the underlying measurement condition or a dedicated explicit status rather than a fragile text prefix.

**Acceptance:** a realized case without actuals must be excluded and explicitly reported as incomplete. A case with all required actuals, period and evidence must display a different, positive state. Every unused row must remain blank.

### OC-02: A status message overwrites a spare-row case key

**Evidence:** `Challenge Review!B36` contains the portfolio status-message formula. The surrounding `B24:B38` range is also the case-ID lookup table. Row 36 should contain the ID from `Cases!B18`.

**Reproduction:** create a complete live case in Cases row 18 and set `Challenge Review!D36` to `blocked`. Its ID is absent from the lookup column because B36 is prose. `Review & Decision!AA18` falls back to `unchecked` and `AB18` remains `yes`.

**Correction:** move the portfolio status message outside the table and restore `=IF(Cases!B18="","",Cases!B18)` in B36. Check that the message's merged range and formatting do not overlap any case row. Retain the hard-block semantics.

**Acceptance:** fill all four spare rows, assign each a different review status and verify every status follows the correct case. The row-18 blocker must result in `AA18 = blocked` and `AB18 = no`.

### OC-03: Unknown current inputs can still enter planning

**Evidence:** the factor formula in `Review & Decision!R6:R20` tests execution hours and alternative inputs but does not require all current resource and cost inputs. The eligibility formula in AB depends on that factor.

**Reproductions:**

| Input cleared in case 1 | Source warning state | Incorrect downstream behavior |
| --- | --- | --- |
| `Cases!S6`, current additional team hours | `Cases!W6` becomes blank | Factor remains 1, eligibility remains yes, and net team hours become minus 80 as though current team effort were zero |
| `Cases!T6`, current recurring cash cost | Current total cost becomes blank | Eligibility remains yes; current cash is treated as zero |
| `Cases!M6`, person group | Gross staff-hours pull-through becomes blank | Eligibility remains yes and downstream formulas fall back to the staff interpretation |

**Correction:** centralize completeness rules for the selected proposal and input mode. Require the current person group, team hours and recurring cash cost, plus the applicable event/annual-hours inputs and relevant rate parameters. Blank should remain unknown. Explicit zero must remain allowed where meaningful. Scope a missing input to the metrics it invalidates; do not silently produce an apparently complete economic result.

**Acceptance:** repeat the three reproductions above, then repeat with explicit zeros. Unknown inputs must block the affected planning figures; confirmed zeros must calculate normally.

### OC-04: Example and incomplete measurement records can enter planning

**Evidence:** `Review & Decision!D24:E28` filters status and eligibility but not Case type. `Results & Reinvestment!C16:C18` consumes those totals. Realized eligibility checks AL:AN for numeric presence, but does not require `Cases!AO` measurement period or `AP` evidence reference.

**Reproduction A:** change case 1 from modeled to validated without changing its Example type. The live portfolio still has zero cases, but reinvestment receives 7,033.33 staff hours.

**Reproduction B:** set case 1 to realized and enter actuals 100 staff hours, 5 team hours and €20 cash. Leave measurement period and evidence blank. The case is eligible and contributes to planning.

**Correction:** make operational planning consistently filter `Case type = Live`. Preserve a separate explicitly illustrative view if teaching with examples is intended. Require a meaningful measurement period and evidence reference for realized figures, in addition to valid numeric actuals. Define whether the actuals represent annualized savings or raw measured-period totals and document the annualization method.

**Acceptance:** changing an Example status must never affect live planning. A Live realized record without period or evidence must remain incomplete. A verified zero actual must be accepted.

### OC-05: Overlap exclusions activate before the underlying case contributes

**Evidence:** `Results & Reinvestment!J5` and J8 use eligibility and proposal type for their auto-exclusion. They do not require a Live validated or realized case. The baseline already says `no - priced in case 6` while no validated or realized resource release has entered the coverage calculation.

**Implication:** demand can be removed as already funded while the corresponding alternative is only a modeled example. This understates the demand denominator relative to the resources credited to coverage.

**Correction:** use one consistent inclusion definition for credited resources and priced-in alternative overlap. The case must be Live, eligible and in the planning status actually used by the coverage calculation. Preserve explicit additional-demand choices. Consider recording overlap against stable case IDs instead of fixed row numbers.

**Acceptance:** moving case 6 through modeled, validated and realized should change its supply contribution and alternative-demand exclusion coherently. Rejecting or blocking the case must restore the independent demand.

## Decisions to clarify before release

**Reviewed and approved are not required by the current gate.** An `unchecked` challenge review and an `open` human decision can still be planning-eligible if the case is otherwise complete. Only `blocked` and `rejected` are hard stops. Decide whether this permissive definition is intentional. If it is, rename/explain eligibility accordingly; if completed review and an implement/pilot decision are intended, enforce them. This is a product decision, not a formula translation fix.

**Numeric validation is incomplete.** There are useful list validations and share bounds, but most rates, hours, event counts and common parameters lack type/range protection. Protect against negative headcount, negative time, invalid FTE denominators and reversed uncertainty bounds. Validation alone is insufficient when paste can bypass it; affected output formulas should also detect invalid values.

**The template supports fifteen cases, not an automatically growing catalogue.** Eleven are populated and four are spare. Many ranges are explicitly bounded to rows 6:20. Extending the tool requires coordinated changes to Cases, the business-model matrix, challenge-review keys, decision formulas, validations and summaries.

**Manual reviews depend on row identity.** Challenge Review case IDs and labels link back to Cases by row, while its manual statuses remain in their existing rows. Sorting Cases alone can move the case identity without moving its manually entered review history. Keep the supplied order until manual review records have their own stable keys and joins. The fixed case-1 diagnostic override and positional overlap formulas also need explicit documentation.

**The 0–5 purpose matrix and thresholds are assumptions.** They are useful discussion inputs, not empirical estimates of control effectiveness. The advisory quadrant should remain visibly separate from selected proposals and from quantified outcomes. Two comparative tests are a helpful start; they do not demonstrate every proposed control change is safe.

**Example text includes external and legal claims.** The source distinguishes external evidence, transfer assumptions and observations. Keep that distinction and the existing references. The review did not re-audit every cited paper, standard or jurisdiction. Publication should retain the qualification that the examples are hypotheses for testing, not recommendations to remove controls.

## Repository identity and first use

**Project:** Security Tradeoff Lab. **Repository:** `security-tradeoff-lab`.

**Description:** Compare security-control changes through employee time, specialist capacity, cash and evidence.

The squirrel weighing two acorns represents finite resources and worthwhile alternatives. It does not suggest that the cheapest control is always preferable.

Start with `Start`, then `Parameters`, and inspect one example on `Cases`. Trace its selected proposal through `Review & Decision`. Review the classification diagnostics only where that case is relevant, complete the challenge review, and compare current and proposed operation using the same meaningful protection outcome. Keep modeled, validated and realized states distinct. Read the blockers above before using the figures for commitments.

The repository should include the source workbook, this audit, quick-start guidance, model definitions, a correction plan, reproducible observations and a clear licensing decision. The public repository should contain synthetic examples, with completed organizational assessments kept separately.
